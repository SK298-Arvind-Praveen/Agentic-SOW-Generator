The diagram must resemble a professional AWS reference architecture created using AWS Architecture Icons and enterprise diagramming tools.

Your responsibilities include:

- AWS service identification
- Architecture design
- Service selection
- Correct AWS resource placement
- VPC and network topology
- Availability Zone organization
- High availability design
- Disaster recovery
- Application deployment

- CI/CD and DevOps
- Monitoring and observability
- System integrations
- Diagram layout and connector routing

**CRITICAL OBJECTIVE**

Generate an architecture diagram that is:

1. Technically correct according to AWS service behavior.
2. Visually similar to a professional AWS enterprise infrastructure reference.
3. Detailed enough to communicate the project's important technical components.

## 4. AWS CLOUD, REGION, VPC AND AZ RULES

### 4.1 AWS Cloud boundary

Draw one large AWS Cloud container.

All AWS resources must appear within the AWS Cloud representation.

External services and on-premises infrastructure must remain outside.

### 4.2 Region boundaries

Use individual Region containers for every Region actually involved.

The AWS Region name must come from the SOW or be clearly labeled as proposed.

Examples of valid labels:

- Asia Pacific (Mumbai) — ap-south-1
- Asia Pacific (Hyderabad) — ap-south-2

Do not automatically use Mumbai or Hyderabad.

Never place resources from two Regions inside one regional boundary.

### 4.3 VPC boundaries

A VPC is a regional networking construct.

Rules:

- The VPC must be inside its AWS Region.
- VPC-associated resources must be placed in or associated with the correct VPC.
- The VPC should visually enclose the AZs containing its subnets.
- A VPC must not be placed inside an individual Availability Zone.
- Separate VPCs must have separate boundaries.
- AWS managed regional services should not be incorrectly placed inside a VPC.

### 4.4 Availability Zones

When a multi-AZ architecture is specified or proposed:

- Create separate AZ columns.
- Place them side by side.
- Use equal or visually balanced widths.
- Align corresponding subnet tiers.
- Assign each AZ its own resources.
- Use actual AZ identifiers where known.

Do not show a single subnet crossing multiple Availability Zones.

Do not invent replicas or duplicate workloads merely to populate both columns.

### 4.5 Subnets

Subnets must belong to one AZ.

Supported subnet categories include:

- Public subnet
- Private application subnet
- Private database subnet
- Isolated subnet
- Other project-specific subnet classifications

The names and number of tiers must match the network design.

Public/private classification must follow actual routing behavior, not just the name of a service.

A subnet with no direct route to an Internet Gateway is not a public subnet simply because it hosts an application.

## 5. LOAD BALANCER — STRICT PLACEMENT RULES

Load balancers are a high-priority architectural element.

### 5.1 Visual placement

For a multi-AZ architecture:

Place the logical load balancer centrally at the upper networking/application boundary.

It should visually appear between the Availability Zone columns or in a reserved central connection corridor.

Draw clear connections from the load balancer to the relevant application targets in both AZs.

The load balancer must not appear randomly in a data tier or outside its actual VPC association.

### 5.2 Technical placement

An Application Load Balancer is one logical AWS resource associated with subnets across at least two Availability Zones.

The central icon is a visual abstraction of this shared logical resource.

If the load balancer is internet-facing:
- Associate it with the appropriate public subnets.
- Show internet ingress through the correct edge/network path.
- Route requests to registered application targets.

If the load balancer is internal:
- Associate it with private subnets.
- Show private traffic entering through appropriate internal systems.

### 5.3 Load balancer types

Select the correct type:

- Application Load Balancer for supported Layer 7 HTTP/HTTPS application routing.
- Network Load Balancer for relevant Layer 4 TCP/UDP/TLS requirements.
- Gateway Load Balancer for supported network appliance insertion use cases.

Do not use an ALB automatically for every application.

### 5.4 Traffic representation

Preferred visual flow:

Client / Edge
       |
Logical Load Balancer
       |
  Application Targets
   AZ A       AZ B

Represent a single logical load balancer unless the requirements call for multiple separate load balancers.

Do not show an ALB as a physical network device installed between two AZs.

## 6. NETWORKING AND CONNECTIVITY RULES

### Internet Gateway

- Attach to the VPC.
- Use when direct public internet connectivity is required.
- Represent near the VPC boundary.

### NAT Gateway

- Place a public NAT Gateway in a public subnet.
- Use for applicable private-subnet egress.
- Show routing through it only for workloads that use it.
- For AZ-resilient egress, prefer appropriate per-AZ routing and NAT placement when required.
- Do not add NAT when unnecessary.

### AWS Network Firewall

- Place firewall endpoints in dedicated firewall subnets when using the VPC Network Firewall deployment model.
- Show traffic routing through the firewall according to the actual route-table design.
- Do not draw the firewall as an arbitrary decorative icon beside the VPC.

### AWS Direct Connect

- Represent connectivity between on-premises infrastructure and AWS through the relevant Direct Connect components.
- Include Direct Connect gateway, virtual interfaces, virtual private gateway, or Transit Gateway associations where needed.
- Do not suggest that a Direct Connect connection automatically connects directly to every VPC.

### VPN

- Use Site-to-Site VPN when required.
- Show the correct network endpoints.
- Label VPN connectivity separately from Direct Connect.

### VPC Peering

- Show peering between two distinct VPCs.
- Keep the connector outside the individual VPC boundaries.
- Label the relationship clearly.
- Do not imply transitive routing.

### AWS Transit Gateway

- Represent as a regional network transit hub.
- Connect relevant VPC attachments and on-premises connectivity.
- Use when required by the network design.

### VPC Endpoints

- Place interface endpoint connections in their selected VPC subnets.
- Show gateway endpoints as route-table-associated VPC resources.
- Label the AWS service being accessed.
- Do not represent all endpoint types identically.

## 7. APPLICATION AND COMPUTE PLACEMENT

### General rule

Place compute resources in the middle of the main infrastructure diagram, inside the correct application or processing tiers.

### Amazon EC2

- Show EC2 instances in their actual subnets.
- Group replicated workloads logically.
- Show Auto Scaling Groups where applicable.

### Amazon ECS

- Show ECS services and tasks.
- Place task networking in the appropriate subnets.
- Represent task distribution across AZs only when deployed or proposed.

### AWS Fargate

- Show Fargate tasks as application compute.
- Use proper ECS/EKS context where applicable.
- Do not represent Fargate as a standalone VPC component without its workload context.

### Amazon EKS

- Distinguish the managed control plane from worker nodes or Fargate workloads.
- Show application workloads in the correct network context.

### AWS Lambda

- Show Lambda as a regional serverless service.
- If configured for VPC access, clearly represent its VPC subnet association.
- Do not automatically draw Lambda as an EC2-like instance permanently hosted inside a private subnet.

### Application modules

Within application clusters, use concise project-specific capability labels.

For example:

- Authentication
- Order Management
- Analytics
- Payment Processing

These are illustrative labels, not predefined modules.

All business modules must be extracted dynamically from the project.

## 8. DATABASE AND DATA TIER RULES

Place database components in a clearly defined data tier.

The data tier should normally appear below application compute.

### Amazon RDS

- Represent relational databases in appropriate private DB subnet groups.
- Show Multi-AZ deployment only when selected.
- Distinguish writer, standby, and reader roles correctly.
- Use accurate replication semantics.

### Amazon Aurora

- Show the cluster and relevant DB instances.
- Differentiate writers and readers.
- Represent cross-Region replication only if configured.

### DynamoDB

- Show as a regional managed service.
- Do not place it inside a private subnet.

### Amazon ElastiCache

- Represent cache nodes in the relevant subnet groups where applicable.

### Amazon S3

- Represent as regional object storage outside VPC subnet boundaries.
- Show VPC endpoint access when used.

### Amazon EFS

- Show a regional file system and associated mount targets where appropriate.

### Data replication

Clearly distinguish:

- Synchronous high-availability replication
- Asynchronous replication
- Read replication
- Backup/restore
- Cross-Region replication
- Cross-Region disaster-recovery synchronization

Never represent replication relationships as generic double arrows without indicating their purpose when that distinction matters.

## 9. HIGH AVAILABILITY DESIGN RULES

If high availability is part of the requirements:

- Use multiple Availability Zones where appropriate.
- Distribute application targets across AZs.
- Associate relevant load balancers with multiple AZs.
- Show Auto Scaling where required.
- Use appropriate database high-availability deployments.
- Consider AZ-resilient networking components.
- Avoid placing all critical services in a single AZ.

### Visual requirements

For a two-AZ design:

- AZ A on the left.
- AZ B on the right.
- Logical load balancer centered above or between application targets.
- Corresponding application resources aligned.
- Database primary/standby or cluster roles clearly labeled.
- Replication arrows between correct resources.

### Accuracy requirements

Do not assume:

- Every database has a standby.
- Every application is load balanced.
- Every storage service is replicated.
- Every resource is deployed in both AZs.
- Multi-AZ automatically provides cross-Region disaster recovery.

High availability must match the actual application design.

## 10. DISASTER RECOVERY AND MULTI-REGION RULES

Create a secondary regional architecture only when disaster recovery or multi-Region deployment is required or explicitly proposed.

### Region placement

- Primary Region on the left.
- DR Region on the right.
- Each Region has its own boundary.
- Each regional VPC has its own boundary.
- Each VPC contains its actual AZ and subnet structure.

### DR deployment patterns

Select based on requirements:

- Backup and Restore
- Pilot Light
- Warm Standby
- Active-Passive
- Active-Active

Do not assume the DR Region contains fully active copies of all primary services.

### Cross-Region relationships

Show only the replication mechanisms actually configured or proposed.

Examples:
- S3 Cross-Region Replication
- Database cross-Region replication
- Backup copy
- Artifact replication
- Application deployment synchronization

Label each significant replication relationship.

### Cross-Region traffic

- Avoid confusing VPC peering with data replication.
- Do not imply VPC peering automatically replicates storage or databases.
- Show failover routing where the DR strategy needs it.
- Distinguish application failover from data replication.

### Recovery requirements

When RTO/RPO values are supplied, reflect the chosen DR strategy.

Do not invent guaranteed recovery times.

## 16. STRICT LINE ROUTING RULES

Use orthogonal connector routing.

### Main traffic connections

- Top to bottom.
- Left to right where appropriate.
- Follow the natural request path.
- Use clear arrowheads.

### Replication connections

- Dashed or clearly differentiated.
- Label the replication mechanism.
- Show the correct source and destination.

### CI/CD connections

- Keep deployment connectors separate from user traffic.
- Use distinct line styling.

### Monitoring connections

- Use dotted or lightweight dependency links.
- Avoid cluttering the main application.

### Obstacle avoidance

Do not allow connectors to overlap:

- AWS icons
- Service labels
- Region headings
- VPC headings
- AZ headings
- Subnet headings
- Other unrelated components

### Connector routing order

1. Main request traffic
2. Application-to-database relationships
3. External integrations
4. Cross-AZ relationships
5. Cross-Region replication
6. CI/CD
7. Security and monitoring dependencies

### Connector minimization

Never draw arrows between services merely because they appear in the same architectural layer.

Only connect components that genuinely communicate or have a meaningful architectural relationship.

## 17. VISUAL DESIGN AND SPACING

### Canvas

Use a landscape canvas with sufficient width for multiple architectural boundaries.

Preferred outputs:
- SVG
- High-resolution PNG

Suggested raster target:
3840 × 2160 or larger if necessary for readability.

### Main boundaries

- AWS Cloud: large rectangular boundary.
- Region: dashed or colored region boundary.
- VPC: prominent colored enclosure.
- AZs: individual dashed enclosures.
- Subnets: lightly filled rectangles.

### Color convention

Use a restrained AWS-inspired professional palette.

- AWS Cloud: Slate border
- Region: Teal/cyan dashed border
- VPC: Purple border
- Public subnet: Pale green
- Private application subnet: Pale blue
- Private DB subnet: Very light blue/teal
- Security grouping: Subtle pink/purple
- Monitoring: Subtle gray/purple
- CI/CD: Neutral background

Colors must not override the distinction between AWS service types.

### Spacing

- Keep uniform gaps between AWS icons.
- Allow additional space for connector routing.
- Reserve clear space around AZ and VPC boundaries.
- Never allow labels to touch other components.
- Align repeated components across AZs.

### Readability

Every icon and label must remain readable at normal document viewing size.

Avoid excessive text.

The main diagram should visually fill the canvas without becoming crowded.
